# Воспроизводимые игровые ситуации

## Цель и критерии готовности

Открывать конкретную ситуацию для отладки и ручной проверки одной командой, затем пользоваться обычным игровым управлением. Сейчас нужные состояния создаются внутри автоматических UI-тестов; отдельного интерактивного запуска нет. Одного seed недостаточно: важны расстановка, ресурсы и действия подготовки. Польза — меньше повторного прохождения и ручного изменения тестов при разборе бага.

Первая итерация содержит ровно два именованных сценария:

- `transformer-chain`: бой с батареей, Step-up Transformer и оружием. Проверяются связь, оплачиваемое усиление и переход к базовому эффекту при нехватке заряда. Переиспользовать подготовку и ожидания из energy-plan/power-reason checks.
- `combat-heal`: бой с повреждённым героем, Medkit и оборудованием для проверки лечебного хода. Кнопка HEAL расходует аптечку и ход, враг отвечает, оружие не атакует и не тратит заряд; броня оплачивается по лечебному плану. Переиспользовать подготовку из crafting checks.

Критерии:

1. Одна документированная команда выбирает сценарий по ID и открывает видимый браузер с готовой игрой. Доступен выбор Canvas/WebGL; неизвестный ID/renderer даёт понятную ошибку и ненулевой код завершения.
2. Повторный запуск выбранного сценария восстанавливает тот же состав предметов, размещение, ориентацию, заряд, HP и состояние боя. Seed фиксируется там, где используется RNG. После обычных действий повторный запуск снова даёт исходное состояние; сохранение на диск не требуется.
3. Для каждого сценария записаны исходные данные, способ подготовки, действия и наблюдаемый результат. Управляемая фикстура явно обозначена; она не выдаётся за достижение состояния полным игровым маршрутом.
4. Ручная проверка использует мышь/клавиатуру без консоли и подмены ресурсов. Исходное состояние сверяется с core; UI самостоятельно не вычисляет энергию, урон или доступность.
5. Обычный `npm run dev` и production-сборка сохраняют обычный старт забега. Подготовка остаётся в инструментах разработки/тестов; постоянные игровые debug hooks не добавляются.
6. Запуск сообщает выбранный сценарий и renderer. При ошибке используются существующие диагностические JSON и PNG, когда страница доступна; ошибка до открытия страницы не требует невозможного скриншота. Выход и Ctrl+C останавливают только собственные процессы и удаляют временный профиль. Ошибки запуска ограничены по времени; ожидание ручных действий не обрывается таймаутом автоматического набора.

## Ручная приёмка

Не проводилась: пользователь согласовал план, а не готовый launcher. Будущий чек-лист должен содержать:

1. Запустить `transformer-chain` документированной командой; выбрать оружие, проверить Step-up Transformer, выполнить боевой ход и сравнить усиление/заряд. Перенести элемент цепи и отменить перенос: начало drag снимает выбор и временно убирает усиление, возврат сохраняет предмет/ориентацию, выбор выполняется заново. Проверить нехватку заряда и отсутствие неверного списания.
2. Запустить `combat-heal`; нажать HEAL при неполном HP: расходуется один Medkit, проходит лечебный ход с ответом врага, HP согласован, оружие не атакует и не расходует заряд. Проверить недоступность лечения без аптечки и блокировку во время переноса. Полный HP проверить в обычном старте (пункт 4); ту же границу в бою проверить автоматически, если её нельзя достичь обычными действиями этой фикстуры из-за ответа врага. Точные исходные значения и подпись HEAL уточнить по готовой фикстуре до передачи на приёмку.
3. В обоих сценариях проверить R при переносе, отказ у края панели, компактный вид, resize и blur. Отмена/потеря фокуса сохраняет владельца и положение предмета; действия не дублируются. Повторный запуск восстанавливает исходное состояние.
4. Остановить launcher, запустить снова; порт освобождён, чужие вкладки и браузер не закрыты. Открыть обычный `npm run dev`: стартует обычный забег 4 × 4. Оба сценария отдельно доступны в Canvas и WebGL.

## Известные проблемы

Наблюдаемый пробел — готовые тестовые состояния нельзя открыть отдельной удобной командой для ручного разбора. Текущий browser runner рассчитан на headless-прогон, два renderer подряд и конечный таймаут; интерактивный режим требует явного управления жизненным циклом. `reset` использует специальную боевую сетку 6 × 6: это фикстура, обычный старт 4 × 4 менять нельзя. Новый launcher пока отсутствует, поэтому его работоспособность и время подготовки ещё не проверены.
