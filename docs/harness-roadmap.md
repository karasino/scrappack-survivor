Состояние на 19.11.2026. Пользователь согласовал следующие этапы: воспроизводимые ситуации → оценка работы агента между сессиями → контроль архитектурных зависимостей. Воспроизводимые ситуации приняты. После обсуждения 17.11.2026 пользователь выбрал продолжить разработку игры. После приёмки процедурных секторов 19.11.2026 реализована и принята отдельная защита от неполного core-отчёта. Ранее согласованная очередь остаётся ориентиром для будущих улучшений. Подробный план каждого последующего этапа создаётся отдельно; базовый AGENTS не расширяется историей этих работ.

## 1. Независимые core-тесты — принято

Исходная проблема: правила проверялись через браузер и повторялись для Canvas/WebGL. Цель — быстрый test:core без Chrome/сервера, сохранение чистых сценариев и отдельные интеграционные UI-проверки.

[Задача](tasks/done/2026-11-17-core-tests.md) принята пользователем 17.11.2026. test:core реализован, 77 Node-тестов и чистый полный check прошли; подтверждены запуск, восстановление проверки в новой сессии и перенос/R в бою.

Польза измеряется временем проверки и сохранением перечня сценариев; не количеством новых файлов или assertions. Критерии и технический подход находятся только в задаче.

## 2. CI на чистом checkout — принято

Проблема: локальный зелёный прогон не обеспечивает такой же результат после нового clone или на другой машине.

Предложение: GitHub Actions с отдельными заданиями быстрой проверки и browser-интеграции. Быстрое задание использует Node 24, npm ci, check:docs, core/harness и build; browser-задание явно готовит Chrome/CHROME_BIN и исполняет реальные Canvas/WebGL-наборы. Не предполагать наличие нужного браузера в образе runner.

Польза: воспроизводимая обратная связь на изменения кода и сохранение артефактов сбоев. Приёмка: успешный чистый прогон, контролируемая ошибка видна как failure, JSON/PNG доступны для скачивания, время ограничено. Достаточны минимальные права чтения репозитория; публикация игры не является частью этого этапа.

Статус: [задача](tasks/done/2026-11-17-ci-checks.md) принята пользователем 17.11.2026 по всему ручному чек-листу. Workflow опубликован, обычный и восстановленный GitHub-прогоны успешны, контролируемый failure сохранил JSON/PNG; отмена старого запуска проверена. Найденный ANSI-startup дефект runner исправлен и покрыт регрессией. Защита ветки и публикация игры в задачу не входят.

## 3. Воспроизводимые ситуации — принято

Проблема: нужные состояния уже создаются внутри UI-тестов, но отдельного удобного запуска для ручного разбора нет. Одного seed недостаточно без начального состояния и последовательности действий.

Согласовано: одна команда открывает подготовленную ситуацию в видимом браузере, затем используется обычное управление. Первая итерация — цепь с Step-up Transformer и лечение в бою. Переиспользовать существующие фикстуры/core API и диагностику. Фиксировать исходные данные, seed при RNG, действия и результат; явно отличать фикстуру от полного игрового маршрута.

Польза: быстрее воспроизводить баг и проверять исправление без повторного прохождения. Приёмка: оба сценария доступны в Canvas/WebGL, повторный запуск даёт одинаковое исходное состояние, ресурсы и доступность проверяются обычным вводом, обычный старт игры сохраняется. Завершение освобождает собственные процессы/профиль; ошибка оставляет доступную диагностику.

Статус: [подробная задача](tasks/done/2026-11-17-reproducible-scenarios.md) принята пользователем 17.11.2026 по всему выданному ручному чек-листу. Launcher двух сценариев и автоматические проверки реализованы, полный check прошёл. Контакт монстра и награда босса — возможное расширение после приёмки первой итерации. Универсальный replay/save editor и обычный игровой debug UI не входят.

## Контроль выполнения core-сценариев — принято

Наблюдение: в ограниченной среде Node показал семь успешных файлов без внутренних сценариев; полноценный запуск подтвердил 101 тест. Ручная оговорка в документации не защищала от ошибочного зелёного результата.

19.11.2026 пользователь поддержал отдельную [задачу проверки core-отчёта](tasks/done/2026-11-19-core-report-guard.md). Дополнительный reporter требует внутренний итог с выполненными сценариями для каждого выбранного файла и финальный итог; фиксированного числа тестов нет. Штатный spec сохраняется, недостаточный отчёт даёт ненулевой exit code с файлом и причиной. Реализация и полный check завершены: 101 core, 38 harness, Canvas/WebGL; проверены обычный запуск, реальный отказ sandbox и отрицательная пустая фикстура с остановкой агрегатора. Все три ручные CLI-проверки приняты пользователем 19.11.2026 без замечаний.

## 4. Оценка качества агента и загрузки контекста

Проблема: зелёные игровые тесты не показывают, сможет ли агент продолжить работу в новой сессии без потери решений и требований. Эффект изменений инструкций и skills пока не сравнивается на постоянном наборе заданий.

Предложение: 4–6 небольших контрольных запросов — вопрос о состоянии, продолжение активной задачи, изменение core, UI, обработка конкретного замечания. Оценивать результат, выбор проверок, сохранение решений, честность статуса приёмки и отсутствие посторонних правок. Для чтений использовать доступные журналы вызовов инструментов; не считать собственный пересказ агента доказательством.

Польза: изменения инструкций/skills и смену модели можно сравнивать по результатам. Приёмка: сохранены запросы, критерии и исходный результат для сравнения, видно объяснение неудачи. Правильность работы и сохранение контекста — основные критерии; объём чтения — дополнительная метрика. Если точные токены недоступны, число файлов/байты чтений обозначать приближёнными метриками. Не собирать секреты или приватную переписку в Git.

Статус: направление и очередь ранее согласованы; отдельная задача не создана, реализация не начата. После приёмки сценариев пользователь выбрал продолжить игру. Предложено наблюдать восстановление решений, выбор проверок и честность приёмки на следующих 2–3 реальных игровых задачах, прежде чем выделять новую инфраструктурную работу; точный формат оценки отдельно не согласован. Начать с небольшого ручного набора, автоматизацию добавлять при частом повторении. Собственный агентный сервер или RAG пока не обоснованы.

## 5. Автоматический контроль границ core/UI

Проблема: граница core/UI поддерживается соглашениями; отдельной автоматической проверки запрещённых зависимостей нет. Текущее чтение импортов не выявило нарушения — это защита от будущих ошибок, а не исправление обнаруженной зависимости.

Согласовано: небольшая проверка запрещённых зависимостей core от Phaser, UI и браузерных модулей, включённая в CI. Конкретный охват определяется отдельной задачей; проверка импортов не доказывает правильное владение всеми игровыми расчётами.

Польза: CI сразу сообщает о случайном нарушении границы. Приёмка: корректный проект проходит, намеренно неправильная зависимость в проверочной фикстуре вызывает ошибку с файлом и причиной. Правила и владение расчётами по-прежнему проверяются тестами и ревью.

Статус: направление и очередь согласованы; подробная задача создаётся отдельно после оценки агента, реализация не начата.

## Strict TypeScript — отдельно после оценки объёма

Strict пока не включён. До решения о миграции нужно выяснить количество и характер ошибок, затем предложить ограниченный объём работ и проверки. Миграция не входит в три согласованных этапа. Рефакторинг крупного GameScene и изменение баланса ради типов также не согласованы.

## Как выбирать следующий шаг

После принятой задачи предложить один этап с наблюдаемой проблемой, пользой и проверкой. Если другой симптом стал важнее, пересмотреть порядок с пользователем. Завершённые решения и фактическую приёмку хранить в файлах задач, а roadmap поддерживать кратким и актуальным.
