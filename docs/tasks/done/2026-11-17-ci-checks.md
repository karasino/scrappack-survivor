# CI на чистом checkout

## Цель и критерии готовности

Автоматически проверять проект в чистой внешней среде после изменений и сохранять понятный результат с диагностикой. На старте задачи проверка зависела от ручного запуска на машине разработчика. В принятой core-задаче установка и полный check проверены во временной копии на той же машине; отдельного workflow и подтверждённого прогона GitHub тогда не было. В baseline также наблюдался сбой загрузки Chrome: одной зелёной отметки недостаточно без доступных логов и снимка ошибки.

- Workflow GitHub Actions устанавливает зависимости через npm ci из lockfile на чистом checkout; окружение и версии видны в логах.
- Отдельное задание правил выполняет check:docs, test:core, test:harness и build с Node 24. Для него не устанавливается Chrome и не запускается browser doctor; тесты самого harness вправе использовать свои локальные сокеты/процессы.
- Отдельное браузерное задание явно готовит Chrome и CHROME_BIN, выполняет doctor, затем test:combat-ui, test:exploration и test:crafting последовательно. Canvas/WebGL и существующая диагностика сохраняются. test:visual отдельно не повторяется; полный seed 123 не запускается повторно в UI.
- У шагов сохраняется ненулевой exit code, задания имеют общий timeout. Сбой установки/doctor различим в логах даже до появления JSON/PNG. При ошибке браузерных тестов доступны диагностические артефакты; их отсутствие при раннем сбое не маскирует первичную ошибку.
- Реальный зелёный прогон на GitHub и контролируемый красный прогон подтверждают работу workflow. Красный прогон показывает имя проваленной проверки и доступные JSON/PNG, завершение ограничено по времени. Локальная проверка YAML не заменяет эти результаты.

## Решения и границы

17.11.2026 пользователь подтвердил приёмку [независимых core-тестов](2026-11-17-core-tests.md) и поручил сохранить следующий шаг для новой сессии с локальным коммитом. По [roadmap](../../harness-roadmap.md) выбран CI. В следующей сессии пользователь поручил продолжить активную CI-задачу. После подготовки локального результата пользователь явно разрешил первую публикацию проекта в origin/main и временную ветку для удалённых проверок CI. После удалённых прогонов пользователь подтвердил все пункты ручной приёмки CI.

- Один workflow, два независимых задания на отдельных GitHub-hosted Ubuntu runners: правила и browser-интеграция. В каждом собственные checkout и npm ci; npm cache допустим, перенос готового node_modules между заданиями не нужен. Общий порт 4175 не конфликтует между разными runners; внутри browser-задания команды последовательны.
- Использовать существующие npm-команды, не запускать полный npm run check дополнительно к ним: иначе core/UI продублируются. Локальный check остаётся полным последовательным входом.
- Триггеры: pull_request, push в main и workflow_dispatch. Default branch main подтверждена GitHub API; на старте origin был пуст, затем проект опубликован. Без path-фильтров, скрывающих изменения lockfile, документов или harness. Concurrency учитывает workflow, событие и ветку/номер PR.
- Node — поддерживаемая проектом 24.x из .nvmrc; runner ubuntu-24.04. Chrome for Testing 157.0.8103.78 linux64 выбран по официальной Stable availability, устанавливается из архива по точной версии с проверкой вывода и явным CHROME_BIN. Библиотеки сверены с deb.deps архива, имена t64 соответствуют Ubuntu 24.04. Обновление описано в verification; нынешние headless/SwiftShader-флаги runner сохранены.
- Использовать минимальные permissions contents: read, не передавать пользовательские секреты. Actions закреплять полным commit SHA, при реализации проверить официальные репозитории и поддерживаемые версии. Не использовать pull_request_target для запуска проверяемого кода.
- Загружать диагностические каталоги artifacts с уникальным именем для job/run attempt и ограниченным сроком хранения. Вывод npm/Chrome setup/doctor доступен в логах шагов. Загрузка артефактов не должна превращать упавший тест в success. Job timeout — последняя граница; не обещать загрузку снимка после принудительной остановки всего runner.
- Для контролируемого сбоя временно испортить ожидание существующей browser-проверки в отдельной проверочной ветке, затем убрать изменение. Не добавлять постоянные игровые hooks или намеренно красный режим в обычный workflow.
- Не менять src, баланс, UI, тестовые ожидания ради зелёного CI, зависимости игры, strict TypeScript, правила веток, публикацию игры или хостинг. Если проявится дефект окружения/runner, сначала сохранить свидетельства и исправлять относящуюся к CI причину; не отключать проблемный renderer или сценарий.

Публикация и удалённые прогоны разрешены пользователем 17.11.2026 после просмотра локального результата. Авторизованный доступ получен через локальный gh; удалённые результаты подтверждены отдельно от локальных. Токен не включать в документы, URL или коммит.

Основания: [безопасное использование Actions](https://docs.github.com/en/actions/reference/security/secure-use), [артефакты workflow](https://docs.github.com/en/actions/tutorials/store-and-share-data). Полные SHA сверены с официальными tag refs: [checkout v7.0.1](https://github.com/actions/checkout/commit/3d3c42e5aac5ba805825da76410c181273ba90b1), [setup-node v7.1.0](https://github.com/actions/setup-node/commit/949feb2413d6458794dcd2491c4babbbce0c15c1), [upload-artifact v7.0.2](https://github.com/actions/upload-artifact/commit/cf430e030ddbb5b0abf93d22962f4752f3646cd9). Входы проверены по action.yml этих коммитов; все используют node24. Версия браузера и linux64-архив подтверждены [официальным JSON CfT](https://googlechromelabs.github.io/chrome-for-testing/last-known-good-versions-with-downloads.json).

2. По официальным источникам выбрать поддерживаемые actions с SHA, Ubuntu label и устанавливаемую версию Chrome для Linux; проверить библиотеки, CHROME_BIN и текущие WebGL-флаги. Сохранить технические решения в этой задаче.
3. Создать workflow с двумя заданиями, явными командами, корректными exit codes, timeout, permissions и сохранением диагностики. Повторно не запускать чистый маршрут в браузерных наборах.
4. Проверить синтаксис/схему workflow подходящим локальным валидатором и разобрать порядок команд/условия загрузки артефактов. Отказные проверки делать во временных копиях, не коммитить испорченное ожидание.
5. Выполнить npm ci в чистой временной копии, затем полный check в разрешённой среде; при обоснованных изменениях harness — его целевые регрессии. Записать реальные команды и ограничения. Такой прогон проверяет локальный harness, но не выдаётся за GitHub-hosted результат.
6. Подготовить результат к просмотру. Когда публикация и запуск разрешены и доступны, проверить на GitHub зелёный workflow и контролируемую ошибку с диагностикой; сохранить ссылки и факты в задаче. Временную красную правку убрать. Отсутствие доступа не препятствует подготовке локальных файлов, но оставляет удалённые критерии открытыми.
7. Обновить README/verification/status и checkpoint. Передать короткую ручную приёмку по Actions UI; после её подтверждения закрыть задачу и сделать локальный коммит.

Вопрос отзыва прежнего токена остаётся у владельца и не решается созданием CI. Известное предупреждение размера JS-чанка остаётся вне этой задачи.
