# Scrappack Survivor — инструкции Codex

Разрабатываем roguelike, где рюкзак служит электрической цепью. Обсуждение и документация — по-русски; весь видимый игроку текст — по-английски.

## Обязательные правила

- Игровые правила и владение состоянием находятся в `src/game/core/`; Phaser-представление — в `src/game/ui/` и `src/game/scenes/`. Урон, энергию и доступность действий UI самостоятельно не рассчитывает.
- Игровой интерфейс рисуется внутри Canvas/WebGL. Проверять совместимость с установленным Phaser; версии и настройки читать из package/lock/config, не из исторических заданий.
- При разработке, возобновлении и завершении задачи использовать `$scrappack-task` из [.agents/skills/scrappack-task/SKILL.md](.agents/skills/scrappack-task/SKILL.md). Если навык не обнаружен IDE, прочитать файл явно. Общие правила действуют независимо от навыка.
- Сначала обсуждение и согласованный план, затем реализация и автоматические проверки, затем ручная приёмка пользователя и исправления. После подтверждения приёмки обновить документацию и сделать локальный коммит, без повторного запроса на уже согласованный шаг.
- Не приписывать пользователю ручную проверку, которую он не подтвердил. Автоматические результаты и ручная приёмка — разные записи. Замечания возвращают задачу к реализации.
- После функциональных изменений, исправлений и изменений UI итоговый ответ обязательно содержит русский ручной чек-лист: конкретное действие обычным управлением и ожидаемый результат, с точными английскими названиями. Сначала изменённое поведение, затем связанные регрессии; основные пункты не требуют консоли или подмены ресурсов.
- По затронутой механике проверить основной сценарий, границы ресурсов/доступности, отказ/отмену и сохранение состояния. Для ввода/UI учитывать drag, R, края панелей, компактный вид, resize и blur. Особенности, похожие на баг, объяснять явно: drag снимает выбор, извлечение из цепи убирает усиление, лечение тратит ход, смертельное попадание не отменяет ответ врага.

При противоречии отметить расхождение и проверить источник, не подгонять требования под ошибку кода. [Старая спецификация](docs/archive/legacy-spec.md) — исторический архив: читать только для восстановления причин решения.

## Проверка и завершение

- `npm run doctor` — окружение; `npm run check:docs` — структура контекста; `npm run check` — полная последовательная проверка. Во время работы запускать затронутые наборы из [матрицы](docs/verification.md).
- Перед ручной приёмкой изменений игрового кода выполнять полный `check`. Не повторять весь игровой прогон после одной записи о приёмке. Локальные проверки используют временные профили и фикстуры; запускать и исправлять относящиеся к задаче сбои без дополнительных согласований.
- После содержательного этапа и перед передачей работы обновлять контрольную точку в том же файле задачи. Факты сверять с рабочим деревом; сырые логи и переписку не хранить в документах.
- После принятой задачи предлагать одно полезное улучшение harness с наблюдаемой проблемой, пользой и способом проверки. Предложение не расширяет текущую задачу автоматически.
