# Файлы задач

## Создание и продолжение

Согласование остаётся в чате. Для изменения создать один файл по [шаблону](_template.md) в `active/`, имя `YYYY-MM-DD-short-slug.md`. По умолчанию активна одна задача. Если появилась несовместимая новая задача, сначала согласовать её приоритет, не терять старую запись.

В [status.md](../status.md) поддерживать одну ссылку и служебную строку `<!-- active-task: docs/tasks/active/имя.md -->`; после завершения — `<!-- active-task: none -->`. Путь в маркере отсчитывается от корня репозитория. Каталоги active/done сохраняются в Git через .gitkeep, когда пусты.

Frontmatter содержит `id` (имя без .md), `title`, `status`, `updated` (YYYY-MM-DD). Поддерживаются простые или заключённые в кавычки строковые значения. Для title с двоеточием использовать кавычки. Все разделы шаблона обязательны и непусты; неизвестное обозначать явно, не заполнять вымышленными результатами.

При возобновлении: прочитать status и активную задачу, сверить git status/diff с контрольной точкой, открыть только относящиеся документы и код. При расхождении обновить запись по фактам. Слова «план выполнен» сами по себе не доказывают состояние файлов.

## Жизненный цикл

| Статус | Значение и переход |
| --- | --- |
| draft | Обсуждение, до согласования реализации |
| approved | Пользователь согласовал план; разрешена реализация |
| implementing | Выполнение или исправления после замечаний |
| awaiting-manual | Автоматическая проверка завершена; выдан чек-лист; ожидается ответ |
| accepted | Пользователь подтвердил необходимую приёмку; файл переносится в done |

Замечания возвращают задачу из awaiting-manual в implementing. Частичное подтверждение записывается частично; не закрывать остальные пункты автоматически. Изменённый после согласования продуктовый смысл снова обсудить; технические решения внутри согласованной задачи не требуют новых формальных разрешений.

Контрольная точка: что сделано, что осталось, следующий шаг и известные блокировки. Обновлять после содержательного этапа и перед передачей работы. Логи команд хранить в artifacts при необходимости, а не копировать в файл задачи. Причины важных решений сохранить кратко; ADR нужен только для выбора с долгосрочными последствиями.

До передачи на ручную проверку обновить актуальные документы поведения, запустить нужные команды и выдать чек-лист. Автоматические результаты не равны ручной приёмке. После подтверждения подготовить accepted, перенести тот же файл в done, обновить status/ссылки и сделать локальный коммит кода с документами. Сам SHA закрывающего коммита в тот же коммит записывать не нужно: связь даёт Git. При ошибке коммита сообщить фактический результат, не объявлять фиксацию успешной.

## Развитие harness

После принятой задачи предложить одно подходящее улучшение: симптом → решение → польза → проверка. Добавлять его отдельной согласованной задачей.

| Наблюдение | Возможное улучшение | Проверка пользы |
| --- | --- | --- |
| Правки core требуют долгого запуска Chrome | Отдельные core-тесты | Время обратной связи при сохранённом покрытии |
| На другом checkout окружение расходится | CI с npm ci/doctor/check | Повторяемый зелёный прогон на чистой среде |
| Долго достигать нужной расстановки | Управляемые сценарии | Время воспроизведения бага и ручной оценки |
| Агент повторяет одинаковые пропуски | Оценка harness на реальных задачах | Результат, пропуски, время, нерелевантные чтения |
| Сложное изменение требует второго взгляда | Независимое ревью | Найденные ошибки по явным критериям |

Для оценки процесса нужны разные сценарии: исправление механики, UI, новая сессия посреди задачи и замечания пользователя. Проверять не только итог кода, но и сохранение решений, честность приёмки и выбор контекста.

## Основания подхода

- [Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md): иерархия и размер инструкций.
- [Codex skills](https://learn.chatgpt.com/docs/build-skills): метаданные сначала, тело при выборе.
- [OpenAI о краткой маршрутизации](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra).
- [Anthropic о контексте](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) и [передаче между сессиями](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents).
- [OpenAI об оценке навыков](https://developers.openai.com/blog/eval-skills).

Это проектные соглашения, а не требование отдельного агентного рантайма. История до миграции сохранена [в архиве](../archive/legacy-spec.md).
