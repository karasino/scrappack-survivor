# Развитие harness

Состояние на 17.11.2026. Это рекомендуемая последовательность улучшений, не разрешение выполнить все этапы за один запрос. Подробный план создаётся в отдельном файле задачи перед каждым следующим этапом; базовый AGENTS не расширяется историей этих работ.

## 1. Независимые core-тесты — принято

Исходная проблема: правила проверялись через браузер и повторялись для Canvas/WebGL. Цель — быстрый test:core без Chrome/сервера, сохранение чистых сценариев и отдельные интеграционные UI-проверки.

[Задача](tasks/done/2026-11-17-core-tests.md) принята пользователем 17.11.2026. test:core реализован, 77 Node-тестов и чистый полный check прошли; подтверждены запуск, восстановление проверки в новой сессии и перенос/R в бою.

Польза измеряется временем проверки и сохранением перечня сценариев; не количеством новых файлов или assertions. Критерии и технический подход находятся только в задаче.

## 2. CI на чистом checkout — в реализации

Проблема: локальный зелёный прогон не обеспечивает такой же результат после нового clone или на другой машине.

Предложение: GitHub Actions с отдельными заданиями быстрой проверки и browser-интеграции. Быстрое задание использует Node 24, npm ci, check:docs, core/harness и build; browser-задание явно готовит Chrome/CHROME_BIN и исполняет реальные Canvas/WebGL-наборы. Не предполагать наличие нужного браузера в образе runner.

Польза: воспроизводимая обратная связь на изменения кода и сохранение артефактов сбоев. Приёмка: успешный чистый прогон, контролируемая ошибка видна как failure, JSON/PNG доступны для скачивания, время ограничено. Достаточны минимальные права чтения репозитория; публикация игры не является частью этого этапа.

Статус: [активная задача](tasks/active/2026-11-17-ci-checks.md), implementing. Локальный workflow создан: rules/browser, Node 24, Chrome for Testing, закреплённые Actions и артефакты. Публикация разрешена, локальная gh-авторизация получена; удалённые прогоны и приёмка впереди. Триггеры и проверки записаны в задаче; защита ветки и публикация игры в неё не входят.

## 3. Воспроизводимые сценарии багов и ручной оценки

Проблема: долго заново достигать нужного боя, мастерской или расстановки цепи; одного seed недостаточно без последовательности действий.

Предложение: небольшой каталог именованных сценариев для тестов/локального debug, seed плюс воспроизводимые действия, понятная команда запуска и сохранение текущего состояния/скриншота при сбое. Начать с цепи с трансформатором, контакта монстра, боевого лечения и награды босса. Использовать реальные команды core; управляемые unit-фикстуры отделять от полного игрового маршрута.

Польза: быстрее исправлять и оценивать конкретную механику. Приёмка: одинаковые действия/seed дают тот же результат, сценарий запускается из чистой среды, создание фикстуры не меняет обычный старт игры. Инструменты debug не добавлять в обычный поток игрока без отдельного продуктового решения.

Статус: предложено. Часть сценариев уже существует в тестах; сначала переиспользовать её, а не создавать параллельный каталог той же логики.

## 4. Оценка качества агента и загрузки контекста

Проблема: правильные ответы при ручной приёмке не показывают, какие файлы агент действительно читал и сколько контекста потратил.

Предложение: 4–6 небольших контрольных запросов — вопрос о состоянии, продолжение активной задачи, изменение core, UI, обработка конкретного замечания. Оценивать результат, выбор проверок, сохранение решений, честность статуса приёмки и отсутствие посторонних правок. Для чтений использовать доступные журналы вызовов инструментов; не считать собственный пересказ агента доказательством.

Польза: изменения инструкций/skills и смену модели можно сравнивать по результатам. Приёмка: сохранены запросы и критерии, результаты повторяемо собираются, видно объяснение неудачи. Если точные токены недоступны, число файлов/байты чтений обозначать приближёнными метриками. Не собирать секреты или приватную переписку в Git.

Статус: предложено. Начать с небольшого ручного набора, автоматизацию добавлять при частом повторении. Собственный агентный сервер или RAG пока не обоснованы.

## 5. Контроль архитектуры и типов — отдельный этап по фактическим пробелам

Проблема: граница core/UI сейчас поддерживается соглашениями, strict TypeScript не включён.

Предложение: сначала проверить объём ошибок strict и места нежелательных зависимостей. Затем выбрать отдельную ограниченную миграцию или проверку, запрещающую Phaser/UI/browser imports в core. Не включать эту работу попутно в перенос тестов и не менять игровой баланс ради типов.

Польза: раньше обнаруживать ошибки интерфейсов и смешение ответственности. Приёмка: целевая проверка ловит реальное нарушение, существующие тесты и поведение игры сохраняются. Рефакторинг крупного GameScene и независимое ревью сложных изменений рассматривать только при конкретной потребности.

Статус: предложено; способ миграции и объём требуют отдельного плана.

## Как выбирать следующий шаг

После принятой задачи предложить один этап с наблюдаемой проблемой, пользой и проверкой. Если другой симптом стал важнее, пересмотреть порядок с пользователем. Завершённые решения и фактическую приёмку хранить в файлах задач, а roadmap поддерживать кратким и актуальным.
